# GemstoneGuardian
This is a relatively large project I took on for a class I am taking at NTNU, and is called Gemstone Guardian (GG). GG is heavily inspired by role-playing-games (RPGs) such as pokémon, especially the early ones like Pokémon Red and Blue. 

You play as a boy that uncovers one of his grandmas greatest secrets: that she holds an elemental gemstone: a gemstone with special powers. Using said gemstone you fight all kinds of people, whomst also carry such stones, to become the very greatest carrier.

# For developers and AI agents

Everything below is what you need to work on the code. Read it before changing anything.

## Building and running

JavaFX 19 app, Java 17, one module (`GemstoneGuardian`, see `module-info.java`), one package (`game`). `pom.xml` exists but Maven is not installed on the development machine; the JavaFX jars are in the local Maven cache (`~/.m2/repository/org/openjfx/javafx-*/19/javafx-*-19-win.jar`). Build with `javac` straight into `target/classes` (git-ignored) and copy `src/main/resources` on top:

```powershell
$fx = "$env:USERPROFILE\.m2\repository\org\openjfx"
$mp = (@("base","controls","fxml","graphics") | % { "$fx\javafx-$_\19\javafx-$_-19-win.jar" }) -join ";"
javac --release 17 -encoding UTF-8 --module-path $mp -d target\classes (Get-ChildItem src\main\java -Recurse -Filter *.java).FullName
Copy-Item src\main\resources\* target\classes -Recurse -Force
java --module-path "$mp;target\classes" -m GemstoneGuardian/game.app
```

Run from the project root: the map, highscore and settings are read from `src/main/resources/game/reading/` by relative path, not from the classpath. Savefiles go in `saves/` in the project root (git-ignored), see "Main menu and savefiles" below. A running game must be closed before `target/classes` is rebuilt.

## How a frame works

`app` loads `Game.fxml`, whose controller (`controller`) owns a `Timeline` that ticks every 20 ms and calls `gameHandler.next(deltaTime)`. Everything is drawn onto an off-screen `tempCanvas`, which is snapshotted onto the visible canvas at the end of the frame (`RCanvas` is just a resizable canvas). The draw order in `gameHandler.next` is:

1. `chunks.drawGround()` — z-level 0, the ground of every tile on screen.
2. "behind" particles.
3. `chunks.drawLayer(z, characters)` for z = 1 … max — trees, flowers, characters, anything above the ground, one level at a time. Each level is drawn row by row from the top of the screen, with characters slotted in between the rows by their feet (`character.getFeetY()`), so whatever is further down is in front. Characters have a `z` too (`setZ`), 1 by default; 2 and up is above the trees (for birds and such).
4. "front" particles, then `gui.draw()` on top of everything.

`camera` follows the main character with easing. `gameHandler.getUnitWidth()/getUnitHeight()` is the size of one chunk in pixels and already includes the zoom; a tile is that divided by `getTileCount()` (9). Positions in the world are in chunks (`10000.3` = chunk 10000, tile 2.7), which is why coordinates are around 10000.

## The world

- `chunks` is one world (outside, underground, house floors — see the `worlds` list in `gameHandler`). It holds `chunk`s in a hashtable by position, generating default ones (all the world's `standardTile`) when asked for a missing one. Its `renderDistance` is how far from the camera tiles are drawn; below 1 the world is "dark" and the rest fades to the background colour.
- `chunk` is 9x9 `tile`s. `tile` knows its `tileType`, spawns ambient particles in `drawGround` (the big `switch` on tile id), and answers `isBlocked(xChange, yChange)` / `isBlockedOut(...)` for movement.
- `tileTypes` is the list of all tile types; the index in the list is the id used in `chunks.txt`, so **never reorder or remove lines, only append** (the `//N` comments give the id). Types:
  - `tileType` — one cell of the sprite sheet, optionally blocked, optionally with a `pressurePlate` lambda run when a character steps on it (doors, stairs, healing pads).
  - `waveType` — an overlay drawn over an underlay type. Options: `wave` (bobs up and down, which also lifts it to z = 1; `sway()` right after the type turns the bob into plants bending in a wind gust that rolls towards the bottom right, used for flowers and by `addTreeType`), `z`, `tall` (how many tiles high, grows upwards), `scatter` (random but fixed offset per tile so forests are not a grid). Use `addWaveType`; `addTreeType` is the preset for trees (`treeHeight`, `treeScatter`).
  - `fluidType` — water, lava, toxic, crystal. Drawn by `shader` (per-pixel noise, expensive) or, when the player picks "Fluids: Simple" in settings, by sliding a tile-sized window over the texture's 2x2 cell region (cheap).
  - `solidFrom(left, top, right, bottom)` / `solidTo(...)` right after a type make it one-way: `1` closes that side for entering / leaving. Types without them use the plain blocked flag with no extra checks. Signs use both so you can stand behind them.
  - `teleportTarget()` right after a type lists every tile of it in Settings → Hidden secrets → Teleports (the healing pads use it). The menu finds them with `chunks.findTiles(...)`, shows each with a `miniMap` (a cached still picture of the 3x3 chunks around it, drawn with `tileType.drawMini`) and the world's name from `chunks.getName()`; the menu itself is `guiTeleports` (`gui.openTeleports(targets, title, back)`), shared by that cheat and the teleporter item. Clicking calls `gameHandler.teleportWithEffect(world, x, y)`: green sparks burst from the player (`addEffectParticle`, drawn above everything in the world), a `screenTransition` blacks the screen out tile by tile in a diamond closing in on the player, runs `character.teleport(world, x, y)` (which also runs the tile's pressure plate) while it is black, and opens again as a square. Movement is blocked while a transition runs. Characters with `showInTransition(true)` (only the player) are drawn on top of the black. Standing on a teleport target remembers it (`character.getVisitedTeleports()`) and gives its reward if one is set with `gameHandler.addTeleportReward(world, x, y, item)` and you don't carry one already; the castle pad outside at chunk (9999, 9992) gives the Teleporter. Items can have a right-click action in the inventory (`item.onInventoryUse(text, action)`, shown in the info panel) and can be kept out of the battle item slots with `notForBattle()`.
- `readChunks` parses `chunks.txt`: a header line `world, x, y, name` (several headers may share one block), then 9 lines of 9 tile ids. Blank lines separate blocks. `N` reloads it in game while borders are shown.

## Main menu and savefiles

- The game opens on `guiMainMenu`: Play (the savefile list, with Start new campaign under it: type a name in a `guiTextField`), Settings (the Visuals page of `guiSettings` on its own, `gui.openVisuals()`), Edit map (a disabled placeholder for a future editor of the campaign file) and Quit. Behind it is a real `gameHandler` built with no savefile (`inMenu()`): the outside world drifts by under the `menuView` camera target, with tiles, wind and particles running, while dialogue, events, fights, walking and zoom are off.
- `controller` implements `gameLauncher` (`openMenu()`, `play(saveFile)`). Starting a campaign or going back to the menu throws the whole `gameHandler` away and builds a new one before the next frame, so a loaded game always starts from the campaign exactly as the code and `chunks.txt` make it, with the save laid on top.
- `saveFile` is one key = value file (`java.util.Properties`) plus its header (name, level, play time, last played, where the player is). `saveState.write/apply` hold what goes in it: every character by name (`character.saveTo/loadFrom`: position and target, world, health, xp, effects, queued moves, spawn, visited pads, inventory with `item.saveState()` for per-item state such as gemstone uses, equipped rock slot), which campaign event listeners have fired, lost fights waiting to be retried, the fight going on (enemy and whose turn; started again from the enemy's `battleEvent`), the dialogue on screen and queued (speaker, text, border, item picture), play time and the finished flag. Items are stored by name and rebuilt with `itemRegistry.make(name)`.
- Starting a campaign asks, one step at a time, for its name, the player's name and the girl's (she is both "Girl (Beginner)" and the final boss "Girl (Master)"). A `character` keeps the name it was made with as `getId()`, used for every lookup (`characterContainer.get/find`) and in savefiles; `setDisplayName` changes only what `getName()` shows. The picked names are stored as `names.player` / `names.girl` and set by `gameHandler.readNames` before the save is applied.
- Switching between the menu and a game plays the whole teleport across both: the game being left closes and goes black (`screenTransition.start(middle, minZoom, end)`, `end` asks the launcher to switch), and the controller has the new game open out of the black (`gameHandler.openFromBlack()` → `startFromBlack`). Each side is black for half the usual time and the stars are shared, so it looks like one teleport. Starting from the menu goes through `gameHandler.playWithEffect(save)`; "Save and quit to menu" saves first and adds the sparks. In the menu the black closes in on the middle of the screen. The menu panel and the player overlap on the black: quitting, a fresh menu (`gui.makeMenu()`) slides down over the player before the switch; entering, the menu page that was left is handed to the new game (`openFromBlack(menu)`, `gui.setMenuOverlay`) and slides up off the player.
- Sliding: any `guiElement` can `slideFrom(edge.TOP / BOTTOM)`; from then on hiding it slides it out to that edge and showing it slides it in (`SLIDE_TIME` 0.5 s, eased). `gui` moves the slides in `next` and draws with `drawSliding`. The menu uses the top, the hotbar (`guiHud`) the bottom: it comes up once the menu has gone, and goes down when the inventory opens, a fight starts or the game is being left (`gameHandler.isLeaving()`).
- Campaign listeners get a key in `gameHandler.nameCampaignListeners()` from their world, position and radius (plus a count for several on one spot), so adding a listener elsewhere does not mix up old saves. A listener added to the code later counts as not fired in old saves; a character or item removed from the code is skipped when loading.
- Saving happens on "Save and quit to menu" in the escape menu, when the window is closed (`app` → `controller.shutdown()`), and every two minutes (`AUTOSAVE_SECONDS`). A new campaign is written as soon as it starts. Writes go to a `.part` file that is moved over the old save.
- The savefile list is a `mapGrid` (shared with `guiTeleports`): a `miniMap` of the 3x3 chunks around where the player saved, the name, and "Lvl, play time, date" under it, with an X in the corner that asks before deleting.

## Chests

Every tile of a container type (`container()` after it in `tileTypes`: Chest and ChestLava) is a `chest` (an `itemContainer` of `chest.ROWS` = 3 rows of 8), made in the `gameHandler` constructor after the map is read and filled there with `put(row, column, item)`. Clicking a chest while standing on one of the 8 tiles around it (`gameHandler.clickWorld`, called by the controller when the GUI did not use the click) opens the inventory with the chest above it. Chests can always be opened again and keep what is left in them; their contents are saved with the campaign. `onFirstClose(...)` runs the first time a chest is closed after looking in (it restores the player, as picking up a stone used to; grandma's chest also has her walk over and talk about the first stone). Chests marked `healing()` heal on that first close and give off small green sparks until then (like the yellow ones event listeners give off) (`chest.willHeal`, spawned in `tile.drawGround`). The boltstone's chest holds copper right next to it, so the player sees the two interact. While a chest can be opened (the player is on one of the 8 tiles around it) it gets lighter and back once a second (`gameHandler.chestHighlight`; `waveType` fades in a copy of the chest made lighter with `imgDict.getBrightened`, so the texture always shows). Clicks are mapped to the tile they are on, not with `chunks.getTile`'s rounding, which is made for characters standing on tile corners.

## Characters, items, battle

- `character` has a position, a target it walks towards one tile at a time (`setTarget`, `addMovementToQueue`), a world, health, xp (`level = cbrt(xp)`), effects (fire, poison, healing, confusion), an `inventory` and an equipped `gemstone`. All characters, including NPCs, are created in the `gameHandler` constructor, along with every `event` and `eventListener` (a circle in the world that fires an event and/or dialogue when the main character enters it). `movementEvent` directions are 0 left, 1 up, 2 right, 3 down.
- `inventory` is a list of `itemStack`s: a top part of 8 columns that grows by a row when full (never fewer than `MIN_ROWS`), plus the active part — 4 rock slots (`gemstone`s only) and 4 item slots (anything else). `inventory.give(item)` puts things where they belong and stacks stackables.
- `item` is the base: name, `use` lambda, consumable flag, `look(cellX, cellY, tint)`, `particles(itemParticles)`, `stackable(max)`. `gemstone` (three abilities with uses and hit chance) and `potion` extend it. The catalogues are `gemstones` and `items`; add new ones there. All rocks share one grey-scale texture tinted per gemstone (`imgDict.getTinted`), potions likewise. The tint multiplies the grey, so light colours come out dull; `item.lightTint(lift)` raises the greys first for a bright, clean colour (ice), and `item.seeThrough(alpha)` draws the icon partly transparent (glass, water).
- `battle` holds the fight state only (whose turn, waiting for the player, "more" view) and is drawn by `guiBattle`. Switching rock or using an item costs the turn. NPCs fight with `character.autoMaticMove`.
- `dialogueContainer` is the queue of `dialogue`s; the current one is drawn by `guiDialogue`. Messages added between `beginGroup()` and `endGroup()` (or inside `grouped(runnable)`) are joined into one (`dialogue.combine`: first speaker, first border and picture, all `onShow`s), and the box grows to fit; battle groups each move or item use with its damage and effects, and each character's effect tick. A dialogue with an item (`new dialogue(name, text, item)`) gets a gold border and the item drawn in it.

### Trinkets

A `trinket` is an item worn in one of the two trinket slots (`inventory.slotKind.TRINKET`, `inventory.TRINKETS`), shown as a small panel left of the inventory. Any character can wear them: the player by putting them in those slots, others with `character.wear(trinket)` in the `gameHandler` constructor. While worn they multiply the wearer's stats (`speed`, `health`, `damage`; several worn stack): walking speed in `character.move`, max health in `getMaxHealth`, and the instant damage of the wearer's moves through `character.hitBy(attacker, move)`, which `gemstone.abilityN` wraps around each move (burn and poison tick later and are left out, and so is damage a move costs the attacker). Each trinket has a `place` (HEAD, CHEST, SHOULDER) and is drawn on the character there, bobbing with the sprite, in the world and in GUI boxes; `character.setAnchor(place, shareX, shareY)` moves a place on sprites that are not shaped like the people. `trinket.beats()` makes the icon beat like a heart wherever it is drawn (`item.pulseScale`). The trinkets in `items`: Feather of Hermes Boots (head, walk x1.75), Heart of the Warrior (chest, +10% max health, beats; heat or two lightning hits turn it into the Withered Heart, -5% max health and +10% damage, which healite's healing turns back) and Creatine (shoulder, +10% damage). Their icons are drafts.

### Elemental rock

`elementalRock` (`gemstones.elemental()`, "Elemental Rock") holds up to two rocks in three slots and becomes them. Right clicking it in the inventory (`onInventoryUse` → `gui.toggleElemental`) opens its slots in a small panel under the inventory (`guiInventory`), until it is right clicked again or the inventory closes. Its slots are a `slotGroup` (`elementalRock.slots()`): rocks only, never an elemental rock, at most two (the third stays empty). Move n is move n of the rock in slot n (an empty slot gives an "Empty" move with no uses), and using it uses up that rock's move. Everything else works by one rule: the rocks inside only meet each other, and the elemental rock meets everything outside as if it were them. `itemInteractions.place` also places the rocks inside (not drawn), and they act on each other (radiation, conduction, salt, healing, heat and cold, lightning) only in neighbouring slots, as if `SLOT_STEP` apart like neighbouring inventory slots (`neighboursInside`, `interacts`, `apart`); a heating and a cooling rock inside cancel out (`heatAndColdCancel`). Toward the outside `elementalRock` overrides the item: it gives off what they give off (`getEmissions`, without heat and cold when they cancel), reacts to and conducts what they do (`getSensitivity`, `charge`, `conductsKind`, `getConductRange`), and passes on to them what reaches it (`heatsWith`/`expose`: lightning charging copper, heat melting ice, shaking breaking glass; `struckBy`). Their particles and lightning come out of it (`spawnParticles` gives them its box): a strike from a rock inside can land on its neighbour inside or on anything outside, never on the elemental rock itself, and long strikes always go out (`strikeCan`, `face`). What happens inside is shown in the open slots under the inventory: the rocks there give off their particles but no lightning of their own (`spawnParticles(..., false)`); `guiInventory` notes where the slots are (`itemInteractions.showInside`), and strikes between neighbours inside, short strikes that find nothing, and the sparks of a hit inside are drawn there (`inMenu`, `drawChain`), and not at all while the slots are closed. Long strikes and strikes at anything outside come out of the elemental rock. It is shaken when a rock inside would be (`isShakeable`, `shake`), glows with them and pours like water or lava inside. Rocks inside that change (healite charging) are swapped for what they became (`swapChanged`), so the elemental rock gets the new moves. Saving: `saveState` holds the rocks as name~state~heat per slot.

## The GUI

Everything on screen is drawn on the canvas by the `gui*` classes; there are no JavaFX controls left. `gui` owns the elements, forwards mouse events (controller → `gui.click/hover/scroll`, falling through to the game when nothing used them) and draws them in order: `guiHud` (active row at the bottom), `guiBattle`, `guiInventory`, `guiDialogue`, `guiSettings`. `guiElement` is the base (bounds, `layout(screenWidth, screenHeight)` every frame, `draw`, `click`, `scroll`, `hover`); `guiPanel` groups children, `guiButton` is a 9-sliced button with optional custom face, `slotGrid` draws any block of slots. Tooltips: `gui.setTooltip(String)` shows a small label by the mouse, `gui.setTooltip(infoBox)` a full info box (the same box the inventory's info panel draws, via `infoBox.draw`); in battle nothing follows the mouse: hovering a move slides its box up from behind the move until it sits right on top of it (`guiBattle.drawMovePopups`), and hovering a rock or item in the More view slides up the same info panel the inventory shows (`guiInventory.drawItemDetails`, shared) until it sits centred on top of the action panel, always in the same spot (`drawSlotPopups`); both take `POPUP_TIME` = 0.25 s each way. With nothing hovered or held, the inventory's info panel shows the player's stats (`character.getStatBoxes`: level with a bar of the xp into it, health with a bar, the equipped rock with each move's uses left / when full, active effects). An `infoBox` can carry rows (`row(left, right)`, the right text lined up at the edge) and a bar (`bar(fill, color, label)`) under its text. In battle the health boxes show the health in numbers and one line per effect under the bar (`character.getEffectBoxes(true)`), growing with them. Both are cleared every frame and set again by `hover`.

Slots and chests: a `slotGroup` is any run of item slots the GUI can show and click (size/get/set/accepts, plus a `click` that defaults to pick up, put down, stack or swap). The player's inventory hands out one per kind with `inventory.group(kind)`; `itemContainer` is a plain fixed-size chest; `itemSource` never runs out (taking makes a fresh item, left click one and right click a full stack, anything put in is thrown away). `gui.openContainer(group, title)` opens the inventory with that group in a scrolling panel above it. Settings -> Hidden secrets -> Give item (or the I key, `gui.toggleGiveItems`) opens an `itemSource` over `itemRegistry`, which registers every public no-argument method returning an item in `gemstones` and `items`, so new items show up there by themselves.

Sizes in the gui classes are written for a 1000 px wide window at "Medium" and multiplied by `gui.s()` (`settings.referenceWidth`, `guiSize.factor`), so the GUI is a share of the screen width, unless the screen height is the tighter one: then the largest size is fitted so the tallest screen (`settings.fitHeight`, 620: the inventory with a chest above it) fits, and the other sizes are their share of that. `guiSkin` knows where the GUI textures are and 9-slices panels and buttons (corner and edges are drawn at `border` px and flipped for the other sides). `guiText` draws text in the bundled Silkscreen font (`media/Silkscreen-Regular.ttf`, OFL licence next to it). `guiParticle`/`itemParticles` are the particle effects items give off in slots and on the cursor. An item made with `shakeParticles(boost)` can be shaken: held on the cursor, the mouse speed charges its `agitation` (0 to 1, `item.shake`, a little just for being held), which settles back over `item.SHAKE_SETTLE` seconds wherever the item is, so a rock put down keeps going for a while. Everything that draws items goes through `item.spawnParticles` (up to 1 + boost times as many particles) and `slotGrid.drawStack` / `drawGlowBehind` (the glow), so slots, the hotbar and the cursor all show it; magma (6) and uranium (8) use it. `idleParticles(share)` sets how much it gives off when calm (0: only while shaken), `shakeThreshold(t)` ignores charge below t (so just holding it does nothing), and `glows(false)` turns the glow off; the sandstone uses all three. `item.trail(color, width, life)` leaves a stream behind an item moved on the cursor (`guiTrail`, a small liquid simulation: particles laid along the path keep a share of the swing, fall, and hold together with surface tension (pull towards neighbours, push away when too close, some viscosity), so the stream stretches, necks and pinches off into drops. It is drawn as the surface they make (metaballs) in chunky pixels over the box around it: a lit rim on the upper left, a dark outline elsewhere, a light band under the top and a slightly see-through body. About 1 ms a frame. It breaks when the mouse slows below `gui.TRAIL_SPEED`). Water uses it. Particle types can have physics (`itemParticles` gravity, spin, grain shape; `guiParticle.physics`): the sand falls, tumbles and fades late. `shakeLightning(chance)` makes a shaken item give off lightning strikes instead of (or besides) more particles: `guiLightning` is a jagged line made in code (random bends, sometimes a branch), a glow in the item's colour with a white core, flickering for a fifth of a second, shot along the swing when swung hard. A share of them (`LONG_STRIKE_CHANCE` x shaking) are long strikes, 15-50% of the screen width, with a burst of sparks where they end. The boltstone uses it. Anything with either effect is `isShakeable()` and glows.

Items affect each other on screen (`itemInteractions`, owned by `gui`). Every frame each item drawn in a slot or on the cursor is noted with its place (`interactions.place`), and the next frame uses those places. In the catalogue an item can `emits(itemInfluence.RADIATION / HEAT, range)` (range in item sizes) and `reactsTo(influence, sensitivity)`; lightning comes from `shakeLightning`. Being charged (`item.charge`) feeds the same agitation as shaking, so a charged item glows, gives off particles and lightning, and passes its own influences on. Lightning aims for any item within reach (`SEEK_CHANCE`), makes whatever it hits burst into debris in its colours, and charges the ones that react. Limits are natural where possible: a struck item does not strike back at what struck it for `STRUCK_MEMORY` seconds. Behind that, a charge from another item never goes above `TRANSFER` times that item's own level or `EXTERNAL_CAP`, so loops die out; held items give off at least `HELD_EMIT`. `item.onCharged(...)` is the hook for gameplay later (nothing uses it yet). `emits(influence, range, always, falloff)` gives off even when the item is calm, with the strength at a distance being (1 - distance/range)^falloff (copper uses 3 and 1.74: 0.46 next to it, 0.11 one slot further). Conductors (`conducts(range)`) draw every strike on screen to the closest of them (a held striker only `HELD_CONDUCTOR_CHANCE` of the time) and pass it on to the nearest conductor within range, each once per chain and weaker every hop, and now and then (`SIDE_STRIKE_CHANCE`) also strike a random non-conductor within that range, which takes the hit but does not pass it on; `hitDebris(scale)` sets how much flies off a hit. Now: uranium gives off radiation and magma heat; copper pulls on lightning stones (`CONDUCTION`, always on, stronger the closer) and conducts; the boltstone reacts to radiation, conduction and a little to lightning, uranium and magma to lightning, obsidian to heat. A charged item also gets a light outline behind its icon (`item.drawGlowOutline`, drawn by `slotGrid.drawStack`).

Items can turn into other items (the first interaction with gameplay: the new item is a real gemstone with its own abilities). `transformsInto(influence, dose, color, into)` heats an item while the influence reaches it (`item.expose`; `heatedBy(other, factor)` adds more influences, and a lightning hit gives `HIT_HEAT`); at `dose` it becomes `into`, which starts hot. `revertsInto(...)` turns an item back once it has cooled to nothing (`COOL_RATE` per second, or `coolsIn(seconds)` for its own time; `HEAT_GRACE` after the last exposure). Water takes 15 s. The progress shows as the change's colour over the icon (`item.drawChange`). `item.latest()` gives what an item has become; slots (`slotGrid`), the cursor and the equipped rock swap to it, with a big burst and the new item's outline jumping out of it twice (`itemInteractions.changeBurst`, `guiOutlinePulse`, outline made from the texture by `imgDict.getOutline`). The heat is saved with the item (`.heat`), so glass does not survive a save away from its magma. Now: sandstone becomes glass next to magma (calm magma gives off heat too), ice becomes water next to magma or after two lightning hits. They stay that way until something cold turns them back: obsidian and ice give off `COLD` even when calm, which turns water into ice and magma into coal, using the same build-up. While it works, frosty sparks (white and light blue with a little purple) fly from the cold rock to the one it is turning and both glow (`itemInteractions.coldStream`, up to `COLD_GLOW`). Magma glows the same way while it is heating something. Coal turns back into magma from lightning (two hits). An item can have several changes, each with its own heat (water freezes into ice from `COLD` and turns into salt water from `SALT`); `heatedBy`, `coolsIn` and `carriesState` set up the change added last, and the savefile's heat number is the leading change's heat plus `HEAT_SLOT` times its index. Saltstone gives off `SALT`: water next to it (or held over it) turns into salt water, with white grains flying over (`itemInteractions.stream`). Salt water conducts and pulls the boltstone's lightning like copper, does not freeze, and healite's `HEALING` turns it back into water (with hearts). Copper becomes charged copper from one lightning hit (glowing through `restingGlow`, which fades with the heat left, and with slightly stronger moves); it turns back about 5 s after the last hit, and each hit fills it up again. `carriesState()` on a change hands an item's state to what it becomes; a rock turning into another rock always keeps its uses left, so every form of a rock (magma/coal, ice/water, sandstone/glass, copper, healite, uranium) has as many uses of each move. A rock that changes while equipped stays equipped (`inventory.inRockSlotAsLatest` also counts a slot still holding its earlier form), so in a fight the moves switch to the new form's with the same uses left. There are two kinds of lightning, kept apart (`itemInfluence.isLightning`): yellow `LIGHTNING` (boltstone; copper conducts it and pulls with `CONDUCTION`) and purple `COSMIC` (meteorite, `shakeLightning(chance, kind, color)`; healite conducts it with `conducts(range, kind)` and pulls with `COSMIC_CONDUCTION`). A strike only charges, heats and is passed on by items that react to, heat with or conduct its own kind. The meteorite's strikes throw rainbow sparks (`rainbowSparks()`). A purple hit turns healite into charged healite (purple glow) and uranium into rainbow uranium (`rainbow()`: the tint runs through the hues, in `RAINBOW_STEPS` cached steps), both back after about 5 s like charged copper. Glass breaks back into sandstone when jerked around hard on the cursor (`itemInfluence.SHAKE`, exposed by `gui` above `SHAKE_BREAK` of full shaking), or at once on one sudden turn of the mouse (`gui.suddenTurn`: fast, then off the other way within `TURN_WINDOW`). Healite and charged healite give off `HEALING`, which brings coal back into magma; while it works, 5x5 pixel hearts and 3x3 pixel squares in pinks and reds fly from the healite to the coal (`itemInteractions.healStream`, hearts drawn in code from `guiParticle.HEART` via `guiParticle.shape`). The info panel and tooltips are refreshed every frame (`gui.next` calls `hover`), so they follow items that change under a still mouse. Slot groups that return false from `takesPart()` (the give item catalogue) stay out of all interactions.

Lightning also comes out of the player in the world (`gameHandler.playerLightning`, drawn as `worldLightning`: a `guiLightning` fixed to a world position and scaled with the zoom). An equipped lightning stone strikes now and then while walking (`WALK_STRIKE_CHANCE`), and a carried one that is charged (by copper next to it on the hotbar or in the open inventory, or by shaking) strikes out of the player too, more the more charged (`CHARGED_STRIKE_SHARE`). Also during fights, not during teleports.

While the inventory is open, the world behind it is tinted darker (`gui.INVENTORY_DIM`, fading over `DIM_TIME`). Those particles are also thrown: they get part of the mouse velocity plus a random scatter that grows with the shaking (`guiParticle.fling`), which air drag (`FLING_DRAG`) takes off again so they go back to their normal drift. They glow too, in `item.getGlowColor()` (the tint): a ring-shaped halo (faint over the item, strongest just outside it) that `gui` draws for every placed item after everything else (`itemInteractions.drawGlows`), so no slot drawn later can cut it into squares and a light silhouette of the icon faded in over it, both growing with the agitation. Do not use canvas blend modes such as `BlendMode.ADD` for this: JavaFX applies them to the whole box around the drawing, which shows as a square.

`settings` (GUI size, fluid mode) is saved to `reading/settings.txt` on change. The debug switches (colliders, borders) live in `gameHandler` and are not saved.

## The sprite sheet

`media/tiles.png` is 1500x1600 in 100x100 cells; code addresses cells by pixel position (`x, y` of the top-left corner). Cells are drawn with a one pixel inset so neighbours do not bleed. Row y = 1500 is the GUI row: slot (0), selected slot (100), panel corner/top edge/left edge/middle (200–500), button corner/top edge/left edge/middle (600–900), rock (1000), potion (1100), bandage (1200), and the trinket drafts heart (1300) and withered heart (1400); the feather and syringe drafts are at (1000, 1600) and (1100, 1600). Items are drawn grey-scale and tinted in code: brightness is kept, hue is replaced (`imgDict.getTinted`); `getSilhouette` makes the white "empty slot" hints.

**The textures are drawn by the project owner.** When something needs a new texture, pick a free cell, draw a labelled draft there and say which cell it is; do not redraw cells the owner has finished (the rock at (1000, 1500) is finished). `media/noise_texture.png` is the shader's noise.

## Conventions and working agreements

- Class names are lower case (`gameHandler`, `tileType`), exception messages are Norwegian, comments are English. Files use CRLF. Validate arguments with `IllegalArgumentException` like the existing code does.
- Build systems, not one-offs: assume more items, rock types, tile kinds and screens will come, and put behaviour behind settings and small helpers (the way `addWaveType`, `solidFrom`, `look(...)` do).
- Before building a large system, ask the owner the design questions first.
- Do not take screenshots to check visuals; build, start the game and ask the owner to look.
- Work on a branch, make small commits with a short imperative title and a body that says what changed and why. Verify each commit compiles.
